## Executive assessment

The audit identifies real, consequential defects, but its original blanket conclusions and counts are too strong. In particular, it does not establish that the test suite “only checks helpers,” that every Action has CAP_SYS_ADMIN, or that all named constants/stubs are missing features. Existing read-only, replay, sandbox and review-outcome controls must remain intact while addressing the specific gaps.

Highest-priority retained work:

1. **Execution and trust boundaries:** workspace fallback scripts after PR checkout (S1), unsandboxed allowed static checks (S3), issue-comment fork classification (S4), checkout-controlled analyzer cache provenance (S5), and check-run issuer validation (S6). Root/capability/file-ownership gaps S2/S8/S11 need verification on the supported Linux runner backend.
2. **Review state/publication correctness:** ledger overwrite (P1), successful submission without publication (P2), file-level auto-resolution (P3), and stale publication state across fallback attempts (P8).
3. **Evidence correctness:** CI blame/flaky classification (U1–U3), symlinked instruction reads (U6), enterprise binding reset (U7), and eval failure/coverage accounting (U5).
4. **Operational reliability/contracts:** subprocess pipe/startup blocking (P4/P5), conflicting logging patchers (D2), missing prompt tools/schema mismatch (C2/C3), and weak/non-publishing CI gates (T1–T5).

Material corrections: the two comments on sampled PRs are a **Craft changelog preview plus a review record**, not evidence of duplicate progress comments (L2). #809 is an **issue**, not a PR. ## 1. Security

### S1 · Confirmed · High — A privileged `pull_request_target` job runs scripts from the PR's branch

Evidence: `.github/workflows/mergecraft.yml:350` checks out shared workspace; `:613` runs pinned mergeCraft; `:684` and `:852` execute workspace fallback scripts with `GH_TOKEN`; `src/mergecraft/mcp/checkout.py:307` accepts requested PR, `:324` fetches metadata, `:396` checks out its head in `state.dir`. Same-repo PR code can replace scripts subsequently executed on host with job permissions (`workflow:273–282`). Scope: fallback steps require corresponding provider flags; fork reviews are skipped by this repo's workflow. The currently pinned Action is a different revision; the complete historical runtime chain has not been independently replayed. Current checkout implementation and workflow expose the structural chain. Impact on separate App approval is limited by its independent provenance gate (S6). Keep separate trusted checkout/inline fallback code recommendation.

### S2 · Partial · High — Privileged Linux MCP shell retains authority to undo its masks

Evidence: `src/mergecraft/mcp/shell.py:239–243` builds unshare argv; `:322–342` mounts masks; `:356–378` runs requested command without dropping UID or capabilities. On root Linux runs that have required namespace/mount capability, command retains authority to undo masks and write other root-writable filesystem paths. Correction: the Action is not shown to always have CAP_SYS_ADMIN; detection at `:64–82` chooses supported method and `:380–386` refuses unavailable isolation by default. macOS uses sandbox-exec. Do not state every deployed Action runs a root CAP_SYS_ADMIN shell. Literal git-command screening is supplementary and not a robust security boundary; do not include bypass code. Linux privilege drop + filesystem confinement is warranted for supported privileged backend.

### S3 · Confirmed · High — Allowed static checks inherit orchestrator environment without sandboxing

Evidence: `src/mergecraft/mcp/static_checks.py:163–182` withholds checks only when shell disabled AND tier not trusted; otherwise `review_checks.py:127–133` creates plans and calls run_plans without sandbox; `analyzers/run.py:238` uses `plan.env or None`, inheriting environment; `analyzers/resolve.py:453–475` inserts raw changed files into argv. Root is specific to Action/root execution; ordinary local invocation uses current user. Consequently repo-native checks can execute PR Makefile code with orchestrator credentials when allowed to run. Leading-option filenames are a separate argv-injection issue for commands using `{files}`; no shell-string interpolation is involved. Keep fix but adding `--` must respect tool-specific option syntax.

### S4 · Partial · High — Issue-comment fork classification misses the fork floor

Evidence: `analyzers/trust.py:207–218` grants trusted to issue_comment from OWNER/MEMBER/COLLABORATOR; `config/trust_policy.py:123–133` reports no fork when top-level pull_request missing; `:649–653` therefore misses fork floor; `action/inputs.py:425` misses credential-presence invariant. `mcp/checkout.py:307–324` accepts arbitrary PR number and fetches metadata without rebinding trust. Scope: opt-in consumer issue_comment workflows, not this repo's pull_request_target-only review event. A trusted commenter authorizes invocation, not necessarily fork code execution. Correction: danger-full-access is not automatic—sandbox override is separate, requires operator request and configured tier; `config/trust_policy.py:338–345` makes same-repo permissive but default dispatch tier does not grant issue_comment override. setupScript/MCP shell similarly require enabled configuration. Fetch and bind actual target PR identity before trust/credential/setup decisions.

### S5 · Confirmed · High — Managed analyzer cache trusts a checkout-controlled lock

Evidence: `analyzers/execution.py:149–150` puts cache+lock under reviewed tree; `analyzers/provision.py:383–399` accepts cached binary matching tree-controlled lock entry. Thus manifest's artifact-path pin alone does not authenticate the binary returned by that fast path. `mcp/analyzers.py:157` also permits arbitrary repo_root. Correction: `execution.py:141–146` returns baked binary first, so this path requires managed provisioning fallback/nonbaked binary; do not imply every analyzer always reads cache. UID 0 consequence conditional on root Linux backend (S11), not all platforms. Use trusted cache provenance outside checkout; archive pin and extracted binary digest must be bound rather than naively compared as equal.

### S6 · Confirmed · High — The approval gate accepts a `mergecraft-approval` check-run from any app

Evidence: `.github/workflows/mergecraft.yml:1023–1027` and `examples/workflows/mergecraft-hardened.yml:418–421` select name+latest conclusion with no app filter; `scripts/approve_app_review.py:91` independently verifies app ID. A permitted check writer can satisfy this workflow gate under expected name. Do not imply it bypasses the separate privileged App-review workflow or independently configured branch protection: those may still block merging. Also current workflow explicitly supports job-token fallback, so blindly requiring configured App would be a product-policy change; authenticate expected issuer/run under supported modes and fail closed on missing provenance.

### S7 · Confirmed · Medium — The Claude reviewer keeps its Write, Edit and WebFetch tools while skipping permission prompts

Evidence: `agents/claude.py:72–74` denies execution tools only; `:765–768` skips prompts in CI; source search shows tree hashes in production only via OpenCode (`agents/opencode.py:703–724`). `utils/privilege.py:204–215` drops Claude to agent user, but workspace is handed to agent (`main.py:1836–1844`). ### S8 · Confirmed · Medium — The agent user owns `/opt/mergecraft`

Evidence: `Dockerfile:127`, `Dockerfile.analyzers:143` recursively grant /opt/mergecraft to mergecraft; `utils/privilege.py:204–215` runs agent under that same account while Dockerfile:153–158 documents root orchestrator. ### S9 · Confirmed · Medium — The `mergecraft init` scaffold persists `GITHUB_TOKEN` with `contents: write`

Scope init-generated workflow, not hardened self-workflow which sets false at `.github/workflows/mergecraft.yml:366`. Reduce permissions, disable persistence and pin SHA.
