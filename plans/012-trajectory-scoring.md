## Ordered steps

### 1. Define a strict data contract

Create strict models in `trajectory_scoring.py`: `TrajectoryLabelSet(schema_version, auditor_version, split, source_commit, adjudicator_login, cases)` and `TrajectoryLabelCase(case_id, trajectory: TrajectoryRecord, trajectory_sha256, labelled_at, provenance, adjudication: AdjudicationRecord|None, labels)`. `adjudicator_login` and `labelled_at` are nullable only for agent-seeded `development` rows; independent `calibration`/`held_out` rows require both from the actual human response. `AdjudicationRecord` identifies the kind but not the particular human, so the login remains a separate required identity on independent data. Each of the eight checks must appear exactly once in `labels` as `TrajectoryCheckLabel(rule_id, truth: positive|negative|unknown, expected_paths)`. `expected_paths` is a multiset encoded as a list, so duplicate empty strings represent multiple pathless findings. `positive` requires at least one entry; `negative` requires an empty list; `unknown` is excluded from denominators and also has an empty list. Validate rule IDs against runtime `TRAJECTORY_CHECKS`, reject duplicate case IDs, forbid extras, recompute the hash from canonical `TrajectoryRecord.model_dump(mode="json")`, and add/export `TRAJECTORY_AUDITOR_VERSION` beside the check table. Use split values `development`, `calibration`, and `held_out`; one case ID/hash may occur in only one split.

Keep synthetic fixtures under `evals/trajectories/development/` with `provenance="agent-seeded"`. They test the scorer but cannot establish quality. Supply at least one positive, negative, and unknown example per check; an absent prediction is not a negative label unless the human marked it `negative` with enough captured evidence.

Verification: Focused tests reject unknown checks, duplicate IDs, invalid provenance, missing evidence references and incompatible versions.

### 2. Implement deterministic scoring

Call `audit_trajectory(case.trajectory)`. Represent expected positives as path multiplicities for each rule (`expected_paths`, with repeated `""` entries allowed for multiple pathless findings). Group predictions by `(rule_id, path)` as a multiset and match counts independently for each exact key: `TP += min(predicted[key], expected[key])`, with surplus per key as FP and missing per key as FN. Never allow a prediction at one path to satisfy an expected finding at another. Predictions for a rule labelled `unknown` are preserved in raw output but excluded from TP/FP/FN and exact-match evaluation. Per check compute precision `TP/(TP+FP)` and recall `TP/(TP+FN)`, returning JSON `null` for a zero denominator. Micro metrics sum counts before division. Macro precision/recall average only defined per-check values and report how many checks contributed; never turn an undefined value into `1.0` or `0.0`. A run-level exact-match rate excludes cases with zero non-unknown labels, reports its eligible-case count, and counts an eligible case correct only when every non-unknown label matches with no extra prediction on a non-unknown rule. Preserve raw predictions and disagreement rows. Add `mergecraft eval trajectory-score --labels PATH --json`, `make eval-trajectory`, and best-effort `emit_eval_score` fields prefixed `trajectory.<rule_id>.*`.

Verification: Known confusion-matrix fixtures give exact expected counts; empty/unknown datasets do not print fabricated perfect scores.

### 3. Obtain separate human trajectory labels

Prepare real sanitized traces representing all eight checks, including ordinary-read and redaction boundaries. Freeze a manifest before scoring with case IDs/hashes, source commits, disjoint `calibration`/`held_out` membership, minimum independently labelled examples per check, and regression tolerances. These numeric minimums and tolerances require maintainer approval; the schema must require explicit values and provide no permissive defaults. Have a named independent human annotate with the written protocol. Keep development fixtures and #780 rows out of ground truth. Update #735 to remove #780 as its label dependency.

Verification: The command reports independent eligibility and sample counts per check; unlabelled/agent-seeded collections remain advisory.

### 4. Add a bounded CI comparison

Only after the manifest, labels, minimum counts, and tolerances are approved, score the calibration split, freeze its report hash, then evaluate the held-out split once. CI compares current counts/metrics with that frozen baseline and fails only on the predeclared tolerance. Missing/unknown labels, split overlap, hash drift, or an undersized check makes the job advisory/ineligible and cannot produce a passing quality claim. Any CI failure is about auditor regression, never consumer merge approval.

Verification: make eval-trajectory and make eval-gate pass baseline fixtures; a deliberate false-positive/false-negative mutation makes the comparison fail; agents/gates run-scope tests stay green.

## Implementation review refinements

Repeated case IDs or canonical trajectory hashes are rejected across the entire input collection, including repeated files in the same split, to prevent accidental sample weighting. Reports retain source commits, label-set and trajectory hashes, split membership and named human attribution. Independent label provenance is separate from quality eligibility: until a predeclared minimum-count/tolerance protocol and frozen baseline exist, all scoring remains advisory, including human-labelled inputs. Unknown labels cannot establish passing quality. Unexpected runtime rule IDs fail closed instead of being silently excluded from metrics.
